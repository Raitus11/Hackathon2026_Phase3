Agentic Test Plan Generator

Automated graph unit test generation for our Ab Initio jobs — how the testing works, how to run it, and the cases where it still fails.

Why ATPG exists

  • Kickstart testing practices. Start with simple tests; evolve toward advanced custom scenarios later.
  • Reliable regression coverage. Every job validated automatically so breaking changes surface early.
  • Visibility and compliance metrics. Results published to Octane.

What ATPG produces is a standard Ab Initio Graph Unit Test — the same vendor-documented artifact we could write by hand. It automates the authoring, not the testing. So the next three slides are about the framework itself.

No graph changes

Annotations live in the .tst, never the .mp.

Non-destructive

No writes to targets, no reads from sources. Safe in any environment.

How a graph unit test is built

You define the boundaries of a test by placing test annotations on the flows. Two kinds.

Input source

Defines the data used as input. Placed where the test should begin — where test data is inserted. Goes on any flow, or on a static lookup file.

Test probe

Compares data on the flow against the baseline and reports differences. Placed where the test should end — where output is collected.

The portion of the graph within those boundaries runs during the test. Everything outside appears grey and does not run. Because annotations live in the .tst file rather than the .mp, testing requires no change to the graph.

How the test executes

Step 1
Load captured input
Uses captured input data, not the graph's real input datasets or lookup files.
Step 2
Run the bounded region
Only components inside the annotation boundaries execute.
Step 3
Collect at the probes
Output written to test-specific files instead of the original targets.
Step 4
Compare to baseline
Each probe's output compared to its baseline to decide PASS or FAIL.

The pass rule, precisely

Differences that aren't accounted for → FAIL. No differences, or all differences accounted for → PASS.

What runs during capture is different

Components upstream of the input sources do run during capture — they have to, to produce the data being captured. Components downstream of the probes never run.

The baseline and the snapshot

Capture collects input and output; the data captured at the probes becomes the baseline. Both get packed into one file.

tlk/tlk_audit/tst/example_test_9d3d6148987e.pack.pdf
Input
The data fed to the job on every run. ATPG generates it synthetically to maximise coverage — a three-case if gets three records, one per case. Stored as .dat plus .dml.
Baseline
What the output must match on every run, compared field for field. Also .dat plus .dml — so tests match on record format as well as data.

That hex string

An SHA fingerprint of the snapshot contents. The .tst stores only the hash.

The .pdf suffix

Appended so the EME permits check-in. Strip it for a manual single-test run.

Pack before check-in

Packing writes the fingerprint into the .tst. Check in first and you'll check in twice.

Budget the time

Roughly three minutes per job to create the data and the test job. The Confluence guidance is blunt: start it and leave it running overnight.

One failure won't stop the batch

The script continues if a job fails to run, so a single problem graph doesn't cost you the whole pass.

What happens after you press enter

The script does this

  1. Contacts the MCP server and fetches a job key
  2. Has the MCP server check out the sandbox server-side
  3. Has it create a supporting sandbox in the EME, in a test folder adjacent to yours
  4. Finds all graphs in the sandbox on disk
  5. Asks the MCP to generate a test for each graph
  6. Generates a suite file so all tests run with one command
  7. Generates octane.ksh, saving credentials in the EME
  8. Generates run_test.ksh to run the suite and load results to Octane

The MCP server does this, invisibly

  1. Examines the job — all inputs, outputs and record formats
  2. Builds synthetic test input to maximise code coverage
  3. Runs the job on that new input data
  4. Saves the output as the ground truth baseline
  5. Writes a graph unit test file
  6. Packages input and baseline into a snapshot file
  7. Checks the snapshot and test file into the EME

Running the tests

Whole suite, into Octane

run_test.ksh <sandbox>

Runs the suite and submits results to Octane.

A single test, no Octane

air sandbox test snapshot list <tst> cp …pack.pdf $AI_TEST_DATA_ARCHIVE/…pack air test snapshot unpack <tst> air test run <.tst>

Checking code coverage — how much of the transform the generated data actually exercised

air sandbox test run <tst file> -code-coverage -verbose

-code-coverage is documented in the air Command Reference alongside -junit, -capture-inputs, -unpack / -no-unpack and -suite.

Reading a failure

Name: Events_Keyed_by_dt_id Output-to-baseline field differences: 2 [View] Added records: 2 [View] Deleted records: 0 Changed records: 0 ------ Baseline records: 20 Output records: 22 [Go to test probe] [Update baseline]

Failure detail from the Test Manager or Unit Test Editor.

The two causes you'll actually hit

  • Record order changed. Same records, different sequence from the baseline. Fix: train the test to compare on a key rather than position.
  • A volatile field. A timestamp or date differs between run and baseline. Fix: ignore that field — which is what -ignore_fields does at generation time.

If the new output is genuinely correct

Right-click the failing probe → Test Results > Update Baseline. The previous baseline is overwritten.

Known cases where generation fails

  • Plans. Not supported.
  • Database-only graphs where all logic sits inside a single run-sql component.
  • Two-component graphs with no internal logic.
  • Graphs using join-with-db where the logic lives in the database.

Plus the honest one

The tool is still being upgraded and fails to analyse some graphs it should analyse. Those get fixed as time is allocated.

The pattern: ATPG reasons about logic expressed in the graph. Where the logic has been pushed into SQL or the database, there's nothing for it to see.
